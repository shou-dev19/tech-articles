# 技術記事を書く

## このスキルの立ち位置（最初に読むこと）

**記事を自動生成しない。** 技術記事のネタは書き手本人の実体験であり、AI が代わりに体験することはできない。Claude がやるのは次の3つだけ。

1. **構成の壁打ち** — 何を書くか決まっているとき、どの順で出すかを一緒に決める
2. **草稿の肉付け** — 構成と要点が決まった節を、文章として書き起こす
3. **推敲** — 冗長さ・前提の飛躍・トーンのブレを指摘する

「この技術について記事を書いて」と丸投げされたら、**まず何を体験したのかを聞く。** 一次体験のない記事は、既存記事の劣化コピーにしかならない。

## 手順

### 1. 何を書くか固める

先に次を言語化する。曖昧なまま書き始めると必ず途中で崩れる。

- **読者は誰か** — 「できること」と「できないこと」の両方で切る。「エンジニア向け」では粗すぎる
- **読者の現在の痛み** — できれば実際に聞いたセリフをそのまま。これが導入部の引用ブロックになる
- **読んだ後に何ができるようになるか** — 1文
- **書かないこと** — これを決めると記事が終わる

### 2. 型を選ぶ

`references/article-structure.md` に3つの型がある。

| 型 | 用途 | 目安 |
|---|---|---|
| A 解説記事 | 用語・概念を噛み砕く | 1万字〜。前後編を想定 |
| B 体験記 | 作ったもの・やってみたこと | 3,000〜6,000字 |
| C トラブルシュート | 困った→直した | 1,500〜3,000字 |

型は出発点であって拘束ではない。外すときは「なぜ外すか」を言えるようにする。

### 3. 過去記事を参照する（重要）

**文体をルールで再現しようとしない。既存記事を読ませるほうが精度が出る。** 書き始める前に、同じ型の過去記事を1〜2本読む。

```bash
ls qiita-cli/public/
```

型ごとの参照先を、記事が増えたらここに追記していく:

- 型A: `qiita-cli/public/ai-driven-development-glossary-1.md`
- 型B: `qiita-cli/public/828f628efc3ec79a1f8d.md`
- 型C: `qiita-cli/public/628f6f8757346a43f1e1.md`

### 4. 骨組み → 節ごとに書く

見出しだけを先に全部並べ、合意してから中身を書く。一気に通しで書かない。

### 5. 図版は文章で書き下す

作画は後回し。本文中に指示だけ置く。

```markdown
> 🖼 【図3 AI駆動開発の年表】
> 横軸に2022〜2026年を取り、第1世代〜第5世代を帯で並べる。
> キャプション：「用語は突然生まれたわけではない」
```

詳細は `generate-article-figures` スキル。

### 6. 検品

`check-article` スキルを通してから公開する。

## 文体規約

過去記事から抽出したもの。**守れないときは意図的に破る。**

### 人称と距離感

- 一人称は「私」
- 読者へ呼びかける。「これ、めちゃくちゃわかります」「すみません」
- **先に謙遜する。** 「〜みたいな話は、私よりずっと頭の良い方々がすでにたくさん書いてくださっています。なので本記事では書きません」
- 断定できないことは断定しない。「〜らしい」「〜だと思っています」を使ってよい

### 具体性

- **数字を出す。** 「たくさん」ではなく「38本目」「586コミット」「25日連続」
- コマンドはコピペで動く形で貼る。省略記号を混ぜない
- エラーメッセージは実物をそのまま貼る

### 構造

- **たとえ話は1記事1個。** 決めたら最後までその語彙で通す
- 「〜しないこと」を早めに明示する
- 章の終わりに1〜2文のまとめを置く。長い記事ほど効く
- 見出しは体言止めばかりにしない。疑問形・断定形を混ぜる

### やらないこと

- 「いかがでしたか」「まとめると以下の通りです」のような中身のない定型句
- 読者を煽る導入（「知らないと損する」「エンジニア必見」）
- 網羅しようとすること。**書かないと決めたことは書かない**
- 一次体験のない部分を、あるかのように書くこと

## 前後編に割るとき

1万字を超えたら分割を検討する。

- **前編だけで完結した価値があること。** 「後編で説明します」を連発しない
- 前編の最後に、後編で何を扱うかを列挙する
- slug は `<name>-1` / `<name>-2` で揃える
- 図版 id は各記事の slug 配下で独立する（`fig01` から振り直しでよい）
- **後編を書き終えてから前編を公開する。** 前編公開後に後編の構成が変わると、前編の予告が嘘になる
