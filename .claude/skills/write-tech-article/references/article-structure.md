# 記事の構成テンプレート

過去記事から抽出した型。**埋めるための穴ではなく、外すときに「なぜ外すか」を言えるようにするための基準**として使う。

## 型A: 解説記事（用語・概念を噛み砕く）

長め（1万字以上）になりやすい。前後編に割ることを最初から想定する。

```
1. タイトル
   問いかけ or 痛みの明示 ＋ 得られるものを1文で
   例:「AI駆動開発、用語で挫折していませんか？ ——歴史をたどれば「Skills」も「Hooks」も一本の線でつながる」

2. この記事は誰のために書いたのか
   読者像を「できること／できないこと」で具体的に切る
   例:「プログラミングは普通にできる。でも AI エージェントの経験はほぼゼロ」
   → 想定読者の実際のセリフを引用ブロックで置く（自分が聞いた言葉をそのまま）

3. この記事のゴール（と、ゴールにしないこと）
   非ゴールを明示するのが効く。「網羅しない」「最新を追わない」など

4. 先に断っておくこと
   免責・スタンス・お願い。ここで期待値を下げておくと本文が読みやすくなる

5. 記事を貫くたとえ話を1つ決める
   例:「AI エージェント＝めちゃくちゃ優秀な新入社員」
   → 以降、すべての用語をこのメタファーの語彙で説明する
   → メタファーは1記事1個。2個目を持ち込むと読者が混乱する

6. 本論（歴史 or 段階で辿る）
   「なぜその用語が生まれたのか」を困りごと→解決策の連鎖で並べる
   各段階に図を1枚
   例: 第1世代 補完 → 第2世代 チャット → 第3世代 エージェント → …

7. まとめ：全部つながっている
   本論で並べたものが1本の線であることを図1枚で示す

8. 次に読むもの / 後編への橋渡し
```

## 型B: 体験記（作ったもの・やってみたこと）

短め（3,000〜6,000字）。

```
1. タイトル
   「〜した話」「〜を全部見せます」。誇張しない

2. はじめに
   何が起きて、何をしたか。3〜4文で結論まで書いてしまう

3. 前提の共有
   環境・制約・規模。数字を出す（本数、コミット数、稼働日数）

4. 何を作ったのか / 何が起きたのか
   構成図を1枚。表で全体像を出す

5. 詰まったところ
   ここが記事の価値。解決できなかったことも書く

6. どう解決したか
   手順は再現可能な粒度で。コマンドはそのままコピペできる形で

7. おわりに
   誰に向いて誰に向かないかを1文ずつ
```

## 型C: トラブルシュート（困った→直した）

最短。1,500〜3,000字。

```
1. タイトル
   「〜に乗り換えたら〜が無くて困った話（と、その解決法）」
   症状をタイトルに入れる。検索で刺さるのはここ

2. 何が起きたか
   エラーメッセージ・画面の文言をそのまま貼る

3. 原因
   分かった範囲で。推測なら推測と書く

4. 解決法
   コマンド・設定をそのまま貼る

5. 補足
   「すでに丁寧にまとめてくださっている記事があるので詳しくは触れません」
   と書いて外部リンクへ逃がしてよい。全部書こうとしない
```

## 図版の入れどころ

| 位置 | 役割 |
|---|---|
| アイキャッチ | 記事の主張を1枚で。タイトルの言い換えにしない |
| 導入直後 | Before / After。読者の現在地と到達点 |
| メタファー提示時 | たとえ話の全体像。以降ここへ戻れるようにする |
| 各段階・各章 | 1章1枚。無い章があってよい |
| まとめ | 本論の要素が1本につながる図 |

図版の書き方は `generate-article-figures` スキルを参照。執筆中は `> 🖼` ブロックで**中身を文章で書き下すだけ**にして、作画は後回しにする。
