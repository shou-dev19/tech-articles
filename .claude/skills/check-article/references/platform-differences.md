# Qiita / note 記法差分

同じ原稿を両媒体へ出すときに踏む罠の一覧。**転載時は必ずここを通す。**

原稿の正は Qiita 側（`qiita-cli/public/<slug>.md`）なので、この表は基本的に
「Qiita で書いたものを note 版へ落とすとき何を直すか」を並べたもの。

## 確定している差分

| 項目 | Qiita | note | note 版での対処 |
|---|---|---|---|
| **Markdown の表** | 描画される | **描画されない**。`\| 項目 \| 値 \|` がそのまま文字として出る | HTML を書いて PNG にキャプチャし、`note/assets/<slug>/` へ置いて画像として貼る |
| 公開手段 | `qiita-cli` の main へ push（GitHub Actions） | **ブラウザでの手作業のみ**。CLI も公開 API もない | リポジトリへの push は記録が残るだけ |
| 画像 | リポジトリにコミットして raw URL 参照 | エディタから手動アップロード | `note/assets/<slug>/` に用意してから貼る |
| タグ数 | 1〜5 個（**5個が上限**） | 上限は緩い。運用方針として8〜10個 | 増やす |
| 独自記法 | `:::note info` / `:::note warn` / `:::note alert`、`:::expand` | 無い | 引用（`>`）＋絵文字か、太字の一行に置換する |

## 運用上の決まりごと（プラットフォーム仕様ではない）

- **タグは note で8〜10個。** 多すぎると note のアルゴリズム上不利になるという経験則。上限いっぱいまで盛らない
- **note 本文に h1 を置かない。** タイトルはエディタ側の入力なので、本文の最上位は h2 から始める
- **アイキャッチは 2:1（1280x640）。** 本文中の図は 16:9（1280x720）

## 要検証（埋めながら運用する）

実運用で確認できていない項目。踏んだら**このファイルを更新してから**先へ進むこと。

- [ ] note の見出しは何階層まで意味を持つか（h4 以降が視覚的に区別されるか）
- [ ] note のコードブロックでシンタックスハイライトが効くか、言語指定は解釈されるか
- [ ] note が Markdown 貼り付けを解釈する範囲（どこまでがエディタで自動変換されるか）
- [ ] note で脚注・定義リスト・チェックボックスが使えるか
- [ ] Qiita の OGP 画像として拾われるのは記事内の何番目の画像か
- [ ] Qiita の `updated_at` が publish Action でどう書き換わるか（hook の前提の裏取り）

## 転載チェックリスト

Qiita 版から note 版を作るとき、上から順に潰す。

1. frontmatter を note 用に差し替える（`source` / `source_updated_at` を入れる）
2. **表をすべて洗い出す** → HTML 化 → PNG → `note/assets/<slug>/`
3. `:::note` / `:::expand` を引用か太字へ置換する
4. h1 を h2 へ落とす（見出し全体を1段下げる必要があるかは記事による）
5. 画像参照を raw URL から `note/assets/<slug>/` の相対パスへ差し替える
6. タグを8〜10個へ増やす
7. `check-article.py note/articles/<slug>.md` を通す
8. ブラウザで note へ貼り、画像を手動アップロード
9. 公開後、`note_url` と `source_updated_at` を記録する
